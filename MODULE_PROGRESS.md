# Module Progress: Pet Health Tracker — Android

Companion repo to `pethealthapp` (the Streamlit/Python desktop app), tracking the Phase 3 Android build. See that repo's `MODULE_PROGRESS.md`/`PENDING_ITEMS.md` for the full Phase 1/2 history and the original planning docs (`00_master_prompt...` through `23_sync_readiness...`).

## Architecture decisions (2026-07-21/22)

- **Native rewrite, not a Python bridge (Option B):** compared reusing `core/` business logic via Chaquopy (Python-on-Android) against a full native rewrite. Chosen: native rewrite — `core/` is modest in size (a handful of validation rules, one reminders module, straightforward repositories), so the duplication cost is small next to avoiding a permanent third-party bridge dependency (APK bloat, one more thing that can break on an Android OS update). Only the SQLite schema is shared as a spec, not code.
- **Flutter, not plain Kotlin:** asked what porting to iOS later would cost under each. Plain Kotlin/Compose (not structured for sharing) would mean a full Swift/SwiftUI rewrite; Kotlin Multiplatform would share business logic but is a less mature path on iOS than Flutter's. Flutter chosen to keep that door open cheaply — same Dart codebase, `sqflite`/`drift` both support iOS already.
- **`drift`, not `sqflite` directly:** typed, code-generated SQL matches the existing schema's explicit structure (12 tables, CHECK constraints, cross-pet-match triggers) better than sqflite's raw-string queries.
- **Sync: Storage Access Framework (SAF), not deferred, not a provider SDK:** Android sandboxes Dropbox/OneDrive's synced files (scoped storage) unlike Windows' plain-folder access. SAF's one-time folder-permission dialog lets the app read/write a user-chosen synced folder directly, keeping the same file-sync-piggyback design as desktop rather than integrating a specific provider's API. Not yet built — see Pending.
- **New, separate repo** (this one), not a folder inside `pethealthapp` — Android's Gradle/Flutter toolchain shares nothing with the Python/Streamlit side.
- **Package/app ID:** `com.kevinbrown.pethealthtracker` (default, not yet finalized — app name/publisher details to be reviewed before any real APK packaging or Play Store publishing).
- **State management:** Riverpod. Chosen as a reversible implementation detail, not asked as a separate decision.

## Reminder auto-linking for vaccinations — parity gap #7 (2026-07-29)

Ported desktop's `pets.py` "record a vaccine, remind me when it's due again" workflow: saving a vaccination with a `next_due_date` now offers to create a source-linked reminder for it (`title: "{vaccine_name} booster due"`, `due_date: next_due_date`, `source_record_type: 'vaccination'`). Special-cased on vaccinations only in `pet_detail_screen.dart`'s FAB handler, matching desktop's own `if record_type == "vaccinations"` branch — not a generic record-type feature there either.

**One deliberate implementation improvement over desktop, not a parity deviation:** desktop's Streamlit version has to stash the pending vaccination id in `st.session_state` and re-fetch `vaccinations_repo.list_for_pet(...)[-1]` after the rerun (a workaround for Streamlit's one-shot return values, and fragile — `[-1]` means "latest by `date_administered`", not "just added", so backfilling an old date could theoretically surface the wrong record). ## Medications tab, with dosing schedules and self-advancing reminders (2026-09-08)

A genuinely new feature — medications don't exist in either app's original schema (not one of the 12 tables planned back in Phase 1). Built Android-first per explicit user direction; desktop/Windows porting is tracked separately (see `pethealthapp/PENDING_ITEMS.md`).

**Design, resolved via clarifying questions before writing any code** (per the global build-workflow convention — this was too consequential a data model to guess at): (1) Android-only for now, not both platforms simultaneously. (2) Reminders are **one self-advancing "next dose" reminder per medication**, not one reminder per scheduled dose — logging a dose recomputes and moves the same reminder forward, rather than generating a growing checklist. (3) Dose-based durations ("give X, Y times") need a **real compliance log**, not just a descriptive count — every logged dose is a real row. (4) "Dose modification schedules" means both: standard field editing by default, *plus* real titration (stepped doses across a course, e.g. "2 pills for 3 days, then 1 pill for 7 days") available specifically when adding a new medication.

**Schema:** three new tables — `medications` (one row per course: name, strength, `medication_type` CHECK'd to pill/syrup/injection/cream_lotion, start_date, status), `medication_phases` (one or more per medication, run in `phase_order` sequence — a plain course is one phase, titration is several; each phase has `dose_amount`, `times_per_day`, a comma-separated `dose_times` list, and a `duration_type` of either `time_based` (`duration_days`) or `dose_based` (`duration_dose_count`), mutually exclusive via CHECK, same pattern as pets' DOB/approximate-age split), and `medication_doses` (the compliance log — one row per dose actually marked given, `scheduled_for` vs. `given_at` kept separate so the two can drift without losing the record). The `reminders` table's existing cross-pet-match triggers gained a `medication` branch, same shape as every other source type.

**Domain logic (`lib/domain/medications.dart`):** completion and "what's the next dose" are both **computed from the phase list + dose log at query time, never stored** — same philosophy as `computeUrgency()`'s reminder-status computation. `computeActivePhase()` walks phases in order, consuming logged doses against each until it finds the open one (dose-based: count logged vs. target; time-based: calendar days elapsed since the phase's derived start). `computeNextDoseDateTime()` finds the Nth slot in the phase's repeating daily dose-time sequence, where N is doses already logged in that phase — this is what lets a twice-daily reminder correctly stay on "today" after the first dose and only roll to tomorrow after the second, and lets a dose-based phase stop cleanly at exactly N doses regardless of which days they landed on. `MedicationActions` orchestrates the linked reminder: creates it on medication creation, recomputes and moves it after every logged dose, and removes it entirely (setting `status: 'completed'`) once every phase is done — or on explicit stop/delete.

**UI:** a new `MedicationsTab` (screens/widgets/medications_tab.dart), added as an *extra* tab in Pet Detail rather than forced into the existing generic `_RecordTypeConfig` list — medications don't fit that shape (creation takes a nested phase list, not a flat field map; the list needs a "Log dose" action no other record type has). The add form is genuinely new UI for this app: a dynamically repeatable list of phase cards (add/remove), each with its own dose amount, times-per-day, dose-times text field, and a duration-type toggle switching between a days field and a dose-count field. Editing an existing medication is deliberately simpler — name/strength/type/notes/handled-by only; **phases are immutable after creation**, per the resolved scope (changing a schedule mid-course means stopping the medication and adding a new one, which also keeps the dose log's phase references unambiguous).

**A real bug caught live, not by the test suite:** the Windows dev build's actual database file (created many builds ago, before these tables existed) made the Medications tab **hang on an infinite spinner** instead of showing the empty state — `AppDatabase.schemaVersion` had been left at `1` despite adding three tables, so drift compared it against the file's stored `PRAGMA user_version` (also 1), saw "nothing changed," and never ran any migration. The new tables simply didn't exist on disk; querying them didn't cleanly error, it hung. This mattered beyond just this dev machine — the user is actively testing a sideloaded APK on their own phone, so a real installed app could hit the exact same thing on the next update. Fixed by bumping `schemaVersion` to `2` and adding a real `MigrationStrategy.onUpgrade`: creates the three new tables and their indexes, and — easy to miss — **drops and recreates** the two `reminders_pet_match_*` triggers, since SQLite triggers keep their original body forever once created; editing tables.drift alone never touches what's already on disk. Verified two ways: (1) a new regression test (`test/database_migration_test.dart`) that hand-builds a minimal pre-migration database file, opens it with the real `AppDatabase` class exactly as a previously-installed app would on its next launch, and confirms both that existing data survived and that the recreated trigger actually rejects a cross-pet-mismatched medication reminder (proving the trigger body was genuinely replaced, not just that the tables exist); (2) live, against the actual real dev database file (backed up first) — confirmed the Medications tab now loads correctly and the pre-existing pets' data was untouched.

**Live verification:** `test/medications_test.dart` (8 tests — next-dose computation across both dose-time slots before rolling to the next day, dose-based completion regardless of elapsed days, titration handing off from phase 1 to phase 2 automatically, delete/stop cleaning up the linked reminder, and validation hard-blocks) and `test/medications_widget_test.dart` (2 tests — the full add/log-dose/edit/delete flow through the real UI, and adding/filling a second titration phase in the real form) plus the migration regression test above: 79 tests total, 0 failures. Also live-verified visually on the Windows desktop target end to end: added a real titrated (2-phase) medication through the actual form, confirmed it displayed with the correct next-dose text, logged a dose and watched the reminder correctly advance from "today" to the next day, edited the name, and deleted it — confirming the linked reminder was removed too, not orphaned.
